# verify-real-outcome（真实产物核验）

内置 verify-end-state 拦的是「假成功信号」——接口返回 200、退出码 0、界面显示「已启用 / 已绑定 / 同步 100%」。
但它覆盖不到静默失败：脚本跑通了、没抛错、日志写着 OK，可实际上一个文件都没动、一条数据都没上云。
本技能堵这个缺口。

## 一条铁律
「状态描述」≠「结果」。断言「已修复 / 已固化 / 已完成 / 已部署」之前，手上必须已有「预期产物确实存在」的旁证（文件路径 + 行数/大小/关键内容片段）。否则禁止下结论。

## 为什么必须补这一维（事故来源）
- ima 推送管道静默失败 3 天：脚本照常写日志、launchd 照常触发，内容根本没上云。没有任何 error code，所以连 verify-end-state 的「假成功信号」都触发不了——它是无信号，不是假信号。
- 调试时 agent 的连带错误：把 connector-proxy 管理端点的 200 + tools/list 当「连接器活着」的证据。但那个 200 只证明中间层在，绝不证明下游通；且它返回的是 WorkBuddy 内置工具，不是连接器的领域工具。这是「用控制平面推断数据平面」的层混淆。

## 触发场景
凡出现以下任一，先跑本技能再下结论：
- 写文件 / 部署 / 上传 / 启动服务 / 导入 / 跨机投递（指令收件箱队列）
- 调用外部进程、脚本、launchd 任务、代理/网关类中间层
- 看到 exit 0 / 200 / 已启用 / 同步完成 / 进程存在 就想宣布成功

## 核验清单（按此顺序，缺一不可）
1. 产物存在性：预期文件/记录/云端条目真的出现了吗？用 ls / stat / 真实查询取真值，不要信脚本自己的 return / 日志里的「成功」二字。
   - 中文路径 Glob 会误报，最终用 ls -la "<绝对路径>" 取真值。
2. 产物正确性：大小非 0、内容非占位、关键字段非空。空文件 / 仅含模板 = 没真做。
3. 数据平面，不是控制平面：代理/网关返回 200 只证明中间层在。要验证下游——真正执行一次端到端操作（positive control）并观察实际结果：推一条真数据看它到没到、查云端是否真有这条。
4. 时间线对齐：日志时间戳是否真的落在本次执行窗口内（防「日志是上次跑的」冒充本次成功）。
5. 二元判定须 >=2 独立信号：状态文件 + 真实产物；或 退出码 + 文件存在。存疑一律归「未知」，不归成功。

## 决定性测试原则（positive control）
当「有没有成功」存疑时，不要再去读更多状态描述（配置、schema、另一个 200），而是：
- 执行一次已知预期结果的真实操作，看系统是否产出该结果。
- 例：验证 ima 推送 -> 推一条真实笔记，去 ima 云端确认它出现；而非去读 ima-endpoint.json 或调代理 tools/list。
- 若根本没有可观察的真实产出信号，先造一个（写 health 文件 / 落回执 / assert 文件存在），再据此判。

## 与内置 verify-end-state 的关系
- 内置：拦「假成功信号」（有信号但信号是假的）。
- 本技能：拦「无信号」（跑完但没产出，连假信号都没有）。
- 两者互补，缺一不可。凡是「执行类」收尾，两个都过才算闭环。

## 反例速记
- curl ... 200 OK -> 「连接器通了」。（200 来自中间层，下游未必通）
- 脚本 return 0 / 日志 OK -> 「文件写好了」。（用 ls 取真值才是旁证）
- launchctl list 显示任务在 -> 「看门狗在跑且生效」。（要看它真写出 health 文件、真触发过告警）
- ls -la 确认文件存在 + 大小正确 + 关键内容命中 -> 才说「写好了」。
