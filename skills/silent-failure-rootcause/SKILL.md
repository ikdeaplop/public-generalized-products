# 静默失效的根因追溯

## 适用场景

现象满足其一就该用这套流程：

- 功能**既不崩也不报错**，就是不起作用（所有表面指标全绿）
- 同一个形状的问题**反复出现**，每次都在不同入口修
- 被问「为什么总在打补丁」「能不能更深一层」
- 「文档或记忆说已完成，但机器实际不是那样」

共同点：**静默**。能长期存活的坏东西，都长得像好东西。

## 一、先溯源，不要猜（禁止凭语感下结论）

有版本控制就直接用 -S 模式追溯引入时刻：

    cd <知识库或代码根目录>
    git log --all --oneline -S"/users/某用户名" -- 相对路径/文件.sh | tail -1   # 最后一行=首次引入
    git log --all --diff-filter=A --format="%ad" --date=format:"%m-%d %H:%M" -- 文件.sh
    stat -f %SB -t "%m-%d %H:%M" 文件.sh        # 无版本控制时看创建时间

**关键产出**：分清是「用久了腐坏」还是「第一版就畸形」。二者对策完全不同——
前者查变更历史，后者查**编写环境**（多半诞生于另一台机器，被搬运过来却没人复核适配性）。

时间跨度必须用工具算出来再落笔，**不许说「用了很久」**。

## 二、分层归因，不许用一个解释糊过去

至少问到第四层，每层都要拿得出证据：

| 层 | 要回答的问题 |
|---|---|
| 1 表象 | 具体哪几处失效？各有独立证据吗？ |
| 2 直接成因 | **逐个**归因。不许「它们都是因为 XX」——往往是两三种不同的病 |
| 3 共性机制缺陷 | 什么结构性问题让它们同时发生、且都能被漏检？ |
| 4 为何无人发现 | 缺哪一道检查？为什么这道检查一直缺席？ |

第 2 层最常见的错误就是笼统。真实情况往往是两种病：
「异地编写未适配」和「清单漏记」——表面相似，治法完全不同。

## 三、锁定机制缺陷的通用判据

**凡是「以后新增一个 X，就要记得来这里登记一下」的流程，长期必定漏。**
见到以下形态立即警惕：

    for name in ("a.sh", "b.sh"):     # 手工枚举的「应覆盖全集」清单

典型高危位置：钩子注册清单、同步文件列表、巡检项清单、定时任务白名单。

**治法：改成遍历目录或读配置表**，然后用「故意新增一个」验证能否零改动被纳入。

另一条同样常见：**依赖把报错丢进黑洞来掩盖外部命令的问题**。
必查被调用命令是否真的支持那些参数：

    命令 --help | grep -oE -- "--[a-z]+" | sort -u              # 实际支持的参数集
    grep -o "命令名[^\"]*" 脚本.sh | grep -oE -- "--[a-z]+" | sort -u   # 代码里实际用的

## 四、修复做在生产端，不做在末端

| 位置 | 效果 |
|---|---|
| 末端（每发现一条就加一条检测） | 逐行补 = 逐行漏。实例：修了 168、203 两处，漏了 231，还漏了另一个文件里的同类硬编码 |
| 生产端（写脚本那一刻就被约束） | 新缺陷无需记得，自动被拦 |

生产端三件套：**自动发现清单 + 上线前自检 + 把这次的失效形态写进自检规则**。

## 五、验证：不许宣称未做的事

1. **隔离变量后再下结论。**疑似问题在单点验证前不算问题——嵌套命令里的引号转义会把参数拆开，
   表现极像「命令不支持某项」。先单独跑，确认了再写结论。
   **把误判写进知识库比不写更糟**，它会污染后续所有检索。
2. **决定性验证**：模拟一次未来的事故（故意新增一个没登记的对象），确认机制能自动兜住。
   这是「下次不会再发生」的证据，比任何承诺都硬。
3. 修完必须实跑，拿真实输出作旁证；抓退出码时别让管道吃掉原始返回值。

## 五点五、后台定时任务「静默断在半截」的三查

症状：**只在定时拉起时**出问题，日志止步于某一行，后续动作与告警全无。
这类事故不能靠读代码，按序三查：

1. **查 `*.err`，不要只盯 stdout 日志。**
   launchd plist 里 `StandardErrorPath` 和 `StandardOutPath` 是两个文件，
   异常在前一个里，后一个只有半句。
   顺带加 `sys.stdout.reconfigure(line_buffering=True)`：stdout 重定向到文件时
   Python 默认 8KB 块缓冲，进程崩溃/被杀时缓冲区整块蒸发——**日志会假装停在最后一行**。

2. **查「依赖」与「副作用」的先后。**
   `grep -nE "^\s+(from|import) " script.py` 揪出写在函数体内的延迟导入，
   看它是不是排在某个不可逆动作（投递 / 写文件 / 发通知）**之后**。
   典型崩法：先 `subprocess.run(["open", url])` 投递，再 `from xxx import ...` 炸掉，
   于是**副作用已经发生、收尾动作永远执行不到**——界面上就是「任务躺在那没发送」。
   治法：依赖提到启动期（缺依赖就在第一条日志里死），不许延期到副作用之后。

3. **用 `env -i` 复现后台环境。**
   `env -i PATH=/usr/bin:/bin HOME=$HOME <python> script.py --plan`
   **后台环境不继承 shell 的 PYTHONPATH / PATH / 虚拟环境**，
   所以「终端里跑得欢、凌晨必挂」的本质是两个不同的运行时。
   修法必须是 `sys.path.insert(0, 模块所在目录)` 写进脚本本身，不靠环境变量。

配套：调用处**不许裸调**——序列执行的 `execute()` / `run()` 要有 try/except
把单个任务异常转成失败结果，否则一个异常掀翻整晚、**连收尾告警都出不来**。
（2026-10-02 夜间协调器实案：`from idle_gate import` 排在 `open <deeplink>` 之后
→ 任务预填到对话框却永不发送，后 5 个任务与晨报全部静默丢失。）

## 六、本机已知的坑

- 变量名后紧跟中文要写成花括号形式，全角括号会被 shell 认作变量名的一部分（严格模式下报未绑定变量）。
- 巡检脚本用 grep 扫「硬编码用户名」时必须排除自身，否则天天自命中；**恒绿才能让真异常显出来**。
- 别的机器写的脚本经同步树搬来后极易静默变性：同步只做文件搬运，不承担本机适配职责。
- 历史背景：09-21 实测过「经验沉淀后复用率仅 11%，用三处加固拉满触发率」。
  但这三处加固之一是会话启动钩子，而 09-22 建的部署体系把它漏在清单外，
  **于是成果被悄悄回退，而触发率掉回 0 这件事本身也不会报错**——典型的自体吞噬型失效。
